# Achievement Bridge architecture

Achievement Bridge is split into three processes with deliberately narrow responsibilities.

```text
Typer/Rich CLI
    HTTP/JSON on 127.0.0.1:47650
Go control plane
    NDJSON protocol v1 on 127.0.0.1:47651
Persistent Zig core
    Steam ABI, provider data and local state
```

## Python interface

The Python application owns rendering, prompts and user-friendly error messages. It sends intentions such as “list installed games”, “show this achievement catalog” and “preview this toast”. It does not parse Zig console output for these flows and does not know Steam ABI details.

When installed, the CLI locates `achievement-bridge-api.exe` beside itself. When run from the source tree it locates the gateway in `zig-out/bin`. If the API is not running, the CLI starts it once in the background and records its output in `%LOCALAPPDATA%\AchievementBridge\bridge-api.log`.

## Go control plane

The Go process is the stable API boundary for any user interface. It:

- exposes HTTP/JSON endpoints under `/v1`;
- validates transport-level input;
- starts and supervises one Zig core when necessary;
- translates HTTP requests into protocol-v1 core messages;
- binds only to the Windows loopback interface.

Current endpoints:

- `GET /v1/health`
- `GET /v1/games?verify_schema=true`
- `GET /v1/games/{appid}/achievements`
- `POST /v1/achievement-previews`

The API contains no Steam vtable offsets, cache format logic or provider parsing.

## Zig core

The Zig executable remains the authority for Steam and achievement state. In `serve` mode it listens only on `127.0.0.1`, processes commands serially and keeps the current Steam session alive between requests. Serial execution prevents overlapping callback queues and `StoreStats` transactions.

Protocol v1 uses one UTF-8 JSON object per TCP connection, terminated by a newline. The core writes one response and closes the connection.

Request envelope:

```json
{"version":1,"id":"request-id","method":"health","params":{}}
```

Success envelope:

```json
{"version":1,"id":"request-id","ok":true,"result":{}}
```

Failure envelope:

```json
{"version":1,"id":"request-id","ok":false,"error":{"code":"ErrorName","message":"ErrorName"}}
```

The request ID is generated by the Go gateway and must match the response. Unknown fields are ignored so compatible fields can be added within protocol v1.

## Compatibility path

The original Zig commands remain available for diagnostics and scripts. The long-lived provider monitor and its verified GSE/RUNE synchronization still use that compatibility path while their event stream is moved behind the Go API. Discovery, catalogs and toast previews already use the separated architecture.

This staged boundary keeps existing game support working while each remaining operation is migrated without copying Steam or provider rules into Python or Go.
